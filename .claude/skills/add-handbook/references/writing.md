# 本文の書き方

SKILL.md の「本文を書く」にある規則（文体、見出しの形、HonKit と相互参照）を前提に、ページの型と細かい表記をまとめる。

## 規範の使い分け

- japanese-tech-writing: 段落と論証、用語の一貫性、読み手の負荷。書いている最中に従う。
- cognitive-rhythm-writing: ページの冒頭、節の入り方、緩急。解説書でも、各ページは読者の場面か疑問から入る。
- yomiyasu: 書き終えたあとの推敲と検査。yomiyasu は表記の揺れ（ユーザーとユーザ、など）を直さないので、本全体の表記は書き手が揃える。

本文は一人で書く。章ごとにサブエージェントへ分けると、文体と用語が章ごとにずれ、通読で直す量が増える。

## ページの型

### はじめに（`ja/README.md`）

1. 冒頭: 読者が抱えている困りごとを具体的に書き、対象の OSS がそれをどう解くかを一段落で言う。前と後を比べる図を置くとよい。
2. `## 対象読者`: 前提とする知識。
3. `## 対象バージョン`: 「本書の説明と実行例は <名前> <バージョン>（<YYYY> 年 <M> 月 <D> 日リリース）にもとづく。手元のバージョンは `<cmd> --version` で確かめられる。」
4. `## 表記`: 入力行を `$` で始めること、例のユーザー名とホーム。短い実行例を一つ置く。
5. `## 読み方`: 日々の操作に足りる章（リンク）と、残りの章の引き方。

謝辞の節は置かない。

### 章の入り口（各章の `README.md`）

その章の考え方の骨格を 1〜3 段落で示し、図を置く。例は、`acme run` が設定ファイルを読み、依存するタスクから順に実行するまでの段階である。節の一覧はサイドバーにあるので、本文には書かない。

### `<cmd>` とはなにか

最初の一文で種類を言う（「〜を管理するコマンドラインツールである」）。続けて、作者と開発の場所（公式リポジトリへのリンク）、実装言語、ライセンスを書く。そのあと、中心となる考え方を実行例と図で示す。

### 動作環境

対応する OS と CPU（リリースの設定にもとづく）、必要な外部コマンドとそのバージョンを書く。そのバージョンが必要な理由も一文で添える（「タスクの入力が変わったかを `git ls-files --format` で調べるので、Git 2.38 以降が必要になる」）。

### `<cmd>` の導入

パッケージマネージャーごとに `##` を立てる（Homebrew、`mise`、Scoop、Go など）。見出しに対応 OS を書かない。利用者の少ない方法は表にまとめる。最後に、入ったことの確かめ方（`--version`）と、シェルの補完の入れ方を書く。

### コマンドの章と節

1. 読者の場面から入る（「タスクが増えると、どれがどれに依存しているのかが見えなくなる。」）。
2. いちばん基本の実行例と、出力の読み方。
3. オプションや状況ごとの節。見出しは「`-j`: 並列に実行する」の形にする。
4. 気をつけたい挙動は段落の最初の一文を太字にして書く（「**`acme rm` は、ほかのタスクがそのタスクに依存しているかを調べない。**」）。太字はこの用途だけに使う。

### オプションの一覧

ページの冒頭で表（`| オプション | 内容 |`）にまとめ、表のあとに各オプションの節を置く。表の中で短い形と長い形を並べるときは、「、」で区切る（`-j`、`--jobs`）。

### レシピ

困りごと、ワンライナー、各部分の説明、変形と注意の順に書く。ほかのツール（`gh`、`jq` など）を使うときは、何のために使うかを一文で書く。

### 付録

設定キーと環境変数を表（`| キー | 設定しないとき | 内容 |`）にまとめ、詳しく説明したページへリンクする。

## コードブロック

- 実行例は `console`。入力行は `$` と半角スペースで始め、出力はそのまま続ける。`.rumdl.toml` で MD014 を外しているのは、この `$` を残すためである。
- シェルの関数や設定ファイルの断片は、中身の言語（`sh`、`ini`、`toml` など）にする。ファイルに書く断片は先頭のコメントで置き場所を示す（`# ~/.bashrc や ~/.zshrc に書く`）。
- ディレクトリのツリーは `text`。

## 表記

- 常体で書く。和文と英数字のあいだに半角スペースを入れる。括弧は全角（）、見出しのコロンは半角の「: 」。
- コマンド、オプション、設定キー、環境変数、ファイル名、パスはコード（`` `…` ``）にする。製品名（Git、GitHub、Homebrew、Go）と一般名詞（SSH、URL、VCS）はコードにしない。
- 用語と表記は本全体で揃える（「ユーザー」と「ユーザ」、「タスク」と「ジョブ」を混ぜない）。
- 数を言ったら、続く列挙と数を合わせる（「三つの利点」のあとに四項目を並べない）。

## リンク

- ほかのページに触れるときは、題名を「」で囲んでリンクにする: ``[「`--dry-run`: 実行せずに手順を表示する」](../run/dry-run.md)``。
- 見出しを変えたら、`check_book.py` の crossref と summary の警告を手がかりに、題名を引いている箇所をすべて直す。
- 外部へのリンクは公式リポジトリ、リリースページ、関係する公式ドキュメントに絞る。`<https://…>` の形で書いてもよい。

## yomiyasu の検査

yomiyasu を読み込むと、ベースディレクトリが表示される。以下、それを `$Y` と書く。

```bash
# 各ページの lint
cd "$BOOK/ja" && for f in $(find . -name '*.md' ! -name SUMMARY.md | sort); do
  echo "=== $f"; python3 "$Y/scripts/yomiyasu_lint.py" --doc-type article "$f"
done

# 本全体の検査（記録の .yomiyasu/ はカレントディレクトリにできるので、スクラッチパッドで実行する）
python3 "$SKILL/scripts/check_book.py" "$BOOK" --concat "$S/book.md"
cd "$S" && python3 "$Y/scripts/yomiyasu_check.py" run --final book.md \
  --material "$REPO/refs/<repo>/README.md" --material "$REPO/refs/<repo>/CHANGELOG.md" \
  --doc-type article --stance 説明 --fact-gaps
```

- lint の候補は見直しの候補であって、誤りの判定ではない。規範に照らして一つずつ判断する。手順や判定の順番を示す番号付きリストや、区別のための否定（「ディレクトリではなくファイル」）は、残してよい。
- `yomiyasu_check.py run` の「資料にない数値・名前」は、ソースを読んで確かめた事実と、例のための名前（`alice` など）が大半を占める。資料と食い違う主張がないかを見る。
- 直したら `run` をもう一度実行する。提出の直前に、本文を変えずに `verify --final book.md` を実行する。
